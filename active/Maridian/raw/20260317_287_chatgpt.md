## 1. Exact Derived Features to Build

Everything in Variant B ultimately flows through VWAP. These features are grouped by dependency — each group depends on the one above it.

### Layer 0 — VWAP Core (foundation, nothing works without this)

| Feature | Definition | Notes |
|---|---|---|
| `vwap` | Cumulative intraday VWAP: Σ(price × volume) / Σ(volume) | Resets at session open (9:30 ET). Use typical price: (H+L+C)/3 as the price input, not close alone. |
| `vwap_dev_pct` | (Close − VWAP) / VWAP × 100 | Signed. Positive = above VWAP. This is the single most important derived value in the entire system. |
| `vwap_dev_zscore` | Rolling z-score of `vwap_dev_pct` over N bars (start with N=20) | Normalizes the deviation so it's comparable across days with different volatility. |
| `vwap_slope` | Linear regression slope of VWAP over trailing N bars (start with N=10) | Captures whether VWAP itself is accelerating or flattening. Use simple (VWAP_now − VWAP_N_ago) / N as a first pass. |

### Layer 1 — Volume Profile

| Feature | Definition | Notes |
|---|---|---|
| `rvol` | Bar volume / rolling mean volume over trailing 20 bars | Relative volume. >1.5 = elevated participation. |
| `rvol_at_time` | Bar volume / historical average volume at the same time-of-day bucket | Requires precomputed session volume curves. Build the simpler `rvol` first, add this only if you collect enough replay data. |
| `cum_volume_ratio` | Cumulative session volume / expected cumulative volume at this time | Tells you if the day is running "hot" or "light." Secondary priority — skip on first pass if data is thin. |

### Layer 2 — Raw Momentum (multi-scale)

| Feature | Definition | Notes |
|---|---|---|
| `roc_3` | (Close − Close_3_bars_ago) / Close_3_bars_ago × 100 | Fast momentum. Noisy but responsive. |
| `roc_5` | Same, 5-bar lookback | Primary momentum signal. |
| `roc_10` | Same, 10-bar lookback | Slower trend confirmation. |
| `roc_20` | Same, 20-bar lookback | Session trend. Will lag but filters chop. |
| `bar_impulse` | (Close − Open) / (High − Low) | Normalized single-bar directional conviction. Ranges −1 to +1. Undefined if High == Low; default to 0. |
| `acceleration` | `roc_5` − previous bar's `roc_5` | Second derivative. Positive = momentum increasing. |

### Layer 3 — Regime Classification Inputs

| Feature | Definition | Notes |
|---|---|---|
| `vwap_position` | 1 if Close > VWAP, −1 if Close < VWAP, 0 if within ±0.02% | Binary regime flag. The ±0.02% dead zone prevents noise at the boundary. |
| `vwap_cross` | True on bars where `vwap_position` changes sign from previous bar | Event detector. Not a continuous feature — it's a trigger. |
| `bars_since_cross` | Count of bars since last `vwap_cross == True` | Measures regime duration. Higher values = more established trend. Resets at cross. |
| `consec_above` | Consecutive bars with Close > VWAP (0 if below) | Simpler alternative to `bars_since_cross`. Both are useful — keep both. |
| `consec_below` | Mirror of `consec_above` for below-VWAP | Same logic, opposite direction. |

### Layer 4 — Session Context

| Feature | Definition | Notes |
|---|---|---|
| `minutes_since_open` | Minutes elapsed since 9:30 ET | Continuous. Better than buckets for downstream models. |
| `session_bucket` | Categorical: `open` (9:30–10:00), `mid_am` (10:00–11:30), `lunch` (11:30–13:00), `mid_pm` (13:00–14:30), `close` (14:30–16:00) | Use for filtering and conditional logic, not as a model input. |
| `session_high_vs_vwap` | (Session high − VWAP) / VWAP × 100 | How far the day's high extended above VWAP. |
| `session_low_vs_vwap` | (Session low − VWAP) / VWAP × 100 | Mirror for low side. |

**Total: 22 derived features across 5 layers.**

## 3. Phase 1 Build Order

The principle: **each step must be independently testable before the next step begins.** No step should require a later step to verify it works.

```
Step 1 ─── VWAP Core Module
            Build: vwap, vwap_dev_pct
            Test: Compare against a known VWAP value from any free charting tool
                  (TradingView, Thinkorswim) for a specific day.
            Why first: Every single downstream feature depends on VWAP being correct.
                       A wrong VWAP corrupts the entire system silently.

Step 2 ─── VWAP Extended Features
            Build: vwap_dev_zscore, vwap_slope
            Test: Verify zscore mean ≈ 0 and std ≈ 1 over a full session.
                  Verify slope sign matches visible VWAP direction on a chart.
            Why second: These are pure transformations of Step 1 output.
                        If Step 1 is solid, these are low-risk.

Step 3 ─── Raw Momentum Features
            Build: roc_3, roc_5, roc_10, roc_20, bar_impulse, acceleration
            Test: Verify roc_5 sign matches obvious price moves.
                  Verify bar_impulse is always in [−1, +1].
                  Verify acceleration = diff of roc_5.
            Why here: Momentum is independent of VWAP. Could technically
                      be built in parallel with Steps 1–2. Placing it here
                      so you have VWAP available for visual cross-checking.

Step 4 ─── Volume Features
            Build: rvol (simple version only)
            Test: Verify rvol spikes at open and near close (known pattern).
                  Verify rvol ≈ 1.0 on average across a session.
            Why here: Requires only raw volume data. Independent of VWAP/momentum.
                      But placed after momentum so you can sanity-check volume
                      spikes against momentum spikes.

Step 5 ─── Regime Classification Inputs
            Build: vwap_position, vwap_cross, bars_since_cross,
                   consec_above, consec_below
            Test: Visually overlay vwap_position on a price-vs-VWAP chart
                  for a known day. Every cross should align.
                  bars_since_cross should reset to 0 at every vwap_cross.
            Why here: Depends on Step 1 (VWAP) being correct.
                      These are the features that will directly define
                      trading regimes in later phases.

Step 6 ─── Session Context Features
            Build: minutes_since_open, session_bucket,
                   session_high_vs_vwap, session_low_vs_vwap
            Test: Verify minutes_since_open = 0 at first bar,
                  increments correctly. Verify bucket labels match clock time.
            Why last: Lowest dependency, lowest risk. But still needed before
                      any Phase 2 work because regime behavior changes by
                      time of day.

Step 7 ─── Feature Validation Utility
            Build: A single function that takes a processed session and
                   runs all sanity checks:
                   - No NaN/undefined in any feature after bar 20
                   - vwap_dev_zscore mean ≈ 0
                   - bar_impulse in [−1, +1]
                   - bars_since_cross resets at every cross
                   - All features present on every bar
            Why last: This is your guardrail for everything above.
                      Run it on every replay session before you ever
                      touch Phase 2.
```

**Critical constraint:** Do NOT build Steps 5 or 6 before Step 1 is verified against an external source. A wrong VWAP that "looks reasonable" will produce regime labels that seem plausible but are systematically wrong. That's the kind of bug that doesn't surface until you've built two more phases on top of it.

**Prompt:**

> I'm building a feature engineering pipeline for my Apex Adapt SPY intraday trading research app. I need you to build Step 1: a standalone VWAP core computation module.
>
> **What to build:**
> A pure JavaScript module (no dependencies) that exports a single function: `computeVWAPFeatures(bars)`.
>
> **Input:** An array of candle bar objects, each with at minimum: `{ open, high, low, close, volume, timestamp }`. The array represents one intraday session (9:30 ET to 16:00 ET), ordered chronologically.
>
> **Output:** The same array, but each bar object now has two new properties added in-place:
> - `vwap`: Cumulative VWAP up to and including this bar. Formula: Σ(typical_price × volume) / Σ(volume), where typical_price = (high + low + close) / 3. Resets each session (assume the input array IS one session).
> - `vwap_dev_pct`: (close − vwap) / vwap × 100. Signed percentage.
>
> **Edge cases to handle:**
> - If a bar has volume = 0, carry forward the previous bar's VWAP (do not divide by zero). Set `vwap_dev_pct` normally using the carried VWAP.
> - If the first bar has volume = 0, use typical_price as the VWAP for that bar.
>
> **Constraints:**
> - Pure function. No side effects, no global state, no DOM access.
> - No external libraries.
> - Include JSDoc comments explaining the math.
> - Include a simple test harness at the bottom: a hardcoded 5-bar array with known values, and console.log assertions that verify VWAP and deviation are correct to 4 decimal places.
>
> **Do NOT:**
> - Add any other features (momentum, regime, etc.)
> - Connect this to any UI or API
> - Modify any existing files
> - Add any strategy logic
>
> Just the VWAP module and its self-test. Name the file `vwap-core.js`.

---

**Why this prompt works:** It isolates the single highest-risk computation (VWAP) into a pure function with zero dependencies on the rest of your codebase. The self-test with hardcoded values means you can verify correctness before you ever integrate it. And by forbidding everything else, you prevent scope creep on the one piece that has to be right.
